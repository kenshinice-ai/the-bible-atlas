# 进化方向清单(EVOLUTION_DIRECTIONS)

日期:2026-07-26
历史基线:v4 Bible-first 架构已落地(时代→人物群→个人 缩放层级、无实体上限、双语),并在 2026-07-27 完成 13 个时代种子装载；旧记录中的“目标约 306 人物 / 1531 事件”和“media_assets 为空”不再代表当前真相。
当前真相(2026-08-09):本地候选 Bible profile 为 224 人物 / 394 事件 / 101 地点 / 10 路线 / 273 关系 / 13 时代；本轮新增 3 条经核验的 Bible 视觉媒体试点记录（人物、事件、地点各 1 条）及本地图片。公开站点 https://bible-atlas-6h7.pages.dev/ 的本轮前审计计数为 224 / 394 / 101 / 10 / 272，仍是未包含本轮变更的旧 production，未部署、未重烘焙。

工作量标尺:S ≈ 1–2 天,M ≈ 3–7 天,L ≈ 2 周以上。

对标结论(调研摘要):
- **OpenBible.info Geocoding Data**:开放了全部圣经地名的地理数据(含多候选位置、GeoJSON、来源对齐 Pleiades/Wikidata),但它是「数据集 + 静态图层」,没有叙事、人物、关系、时间维度——这正是本项目的差异化空间。
- **ORBIS(Stanford)**:证明「一个可交互的模型」比「一张图」更有传播力;其核心是把抽象量(旅行成本)变成可操作的问题(从 A 到 B 要多久)。启示:给用户一个「可提问的动词」(播放、走一遍、对比),而不只是「可浏览的名词」。
- **Pelagios/Recogito**:众包标注可行但代价高——需要专门工具、审核流和动机设计;他们 12 万地名中人工核验不到一半。启示:社区共建是「有受众之后」的策略,不是冷启动策略。

## 一、产品体验

### 1.1 时间轴播放:把时间轴从「过滤器」升级为「播放器」 —— 推荐,S/M

- **主张**:在 `TimelineRibbon.tsx` 加一个播放按钮,自动推进 `until`(叙事模式)或 `rangeEnd`(历史模式),让地图、列表、关系图随时间「生长」。
- **为什么**:v4 最大的架构红利是 `hierarchy.ts` 的单一派生(`visibleEvents` → 地图/列表/图三处联动),播放器几乎是免费的——只需一个 `requestAnimationFrame`/interval 驱动已有的 `onNarrative`/`onRange` 回调,不需要新数据、不需要动渲染层。这是 1500 事件扩容后「让规模变成体验」的最高杠杆动作:13 个时代依次点亮,一分钟看完圣经三千年。
- **工作量**:S(基础播放)/ M(加速度控制、时代切换时地图 flyTo 到该时代 bounding box、`prefers-reduced-motion` 降级)。
- **依赖/风险**:依赖 1500 事件扩容完成后的渲染性能(见 3.1);注意播放时不要每 tick 都 `history.replaceState`(`App.tsx:63` 现在每次 state 变更都写 URL,播放时需节流)。

### 1.2 人物旅程动画:选中人物即播放其一生的迁徙 —— 推荐,S

- **主张**:`hierarchy.ts` 的 `trajectoryFor()` 已经算出「出生地 → 各事件地点 → 死亡地」的有序停靠点,`AtlasMap.tsx` 已画静态轨迹线;下一步给轨迹加方向箭头、渐进描线动画(SVG dashoffset 或 Leaflet polyline 动画)和沿途事件锚点(点击停靠点打开对应事件抽屉)。
- **为什么**:这是 REDESIGN_PLAN 主张 4 的收尾一步,数据和计算全部就位,只差表现层;「亚伯拉罕:吾珥→哈兰→示剑→埃及」这一分钟的动画就是产品的最佳演示素材和传播物料。摩西出埃及、保罗三次宣教旅程是天然的「王牌内容」。
- **工作量**:S。
- **依赖/风险**:`trajectoryFor` 内部对每个 eventSlug 做 `atlas.events.find`,O(人物事件数 × 全事件数),1500 事件后需先换成 Map 索引(与 3.1 一起做)。

### 1.3 事件详情与经文引用联动 —— 推荐,M

- **主张**:给事件增加结构化经文引用(书卷/章/节),在 `EntityDrawer.tsx` 中渲染为可展开的经文段落(公版译本:中文和合本 1919、英文 WEB/KJV),并可反向从引用跳回事件。
- **为什么**:目前来源只有 `sourceTitles`(字符串数组,如 "创世记")和 `chapters.reference_label`,粒度到不了「节」。对标 OpenBible:它的核心资产就是「地名↔经文」的对齐;本项目若做「事件↔经文」对齐,粒度更高一层且独有。这也是把 `content_mode='documented_record'` 的严谨性变成用户可感知价值的一步——每个事件可核。
- **做法**:新增 `event_scripture_refs(event_id, book, chapter, verse_start, verse_end, osis_ref)` 表(migration 004),种子生成规范中本就要求来源引用,回填成本可控;经文文本不入库,前端按 osis ref 从打包的公版 JSON 中取(和合本/WEB 均为公有领域,合规且离线可用)。
- **工作量**:M(表 + 回填 1500 事件的引用 + 抽屉 UI + 打包经文 JSON 约 4–5 MB,可按书卷懒加载)。
- **依赖/风险**:回填质量依赖 AI 生成再校验;严守既有数据政策「不收录大段受版权保护文本」——只用公版译本。

### 1.4 引导式故事线(Guided Tour) —— 推荐但排后,M

- **主张**:预制 6–10 条「故事线」(出埃及、大卫崛起、被掳与归回、保罗宣教……),每条是一串 `ExploreState` 快照(时代 + until + 地图焦点 + 选中实体),用「上一步/下一步」走完,底层复用 1.1/1.2 的动画。
- **为什么**:`serializeAtlasState` 已能把全部探索状态写进 URL,故事线本质上就是「一组带解说的深链接」,实现成本低;它解决 300 人物/1500 事件的新用户「从哪开始看」问题(ORBIS 的教训:强模型也需要引导性入口)。也是课堂/教育场景的形态基础。
- **工作量**:M(播放骨架 S,内容编排占大头)。
- **依赖/风险**:依赖 1.1;故事文案需双语,建议入库(新表 `tours` + translations)而非硬编码。

### 1.5 图数据分析上色:中心性与社群检测 —— 有条件推荐,M

- **主张**:在 `RelationGraph.tsx` 增加分析模式:按度中心性/介数中心性调整节点大小,用 Louvain 社群检测结果上色,与手工维护的 `character_groups` 对照。
- **为什么**:900+ 关系时,分析视图能回答「谁是结构枢纽」这类浏览回答不了的问题(大卫、保罗的中心性会直观浮现);同时社群检测可以作为**数据质检工具**——检测出的社群与 `character_group_members` 不一致处,往往是分组遗漏或关系缺失。REDESIGN_PLAN 主张 1 本来就设想过「用图社区检测算出 L2 后落库」。
- **工作量**:M(度中心性 S;介数/Louvain 用 graphology 库,注意包体;分析结果的图例与解释文案)。
- **依赖/风险**:节点上色已被「时代色」占用(`colorForCharacter`),需要模式切换而非叠加,避免视觉过载;分析价值依赖关系数据密度,应在 900+ 关系装载后再做。

### 1.6 地图叙事图层收尾:区域面与不确定性可视化 —— S/M

- **主张**:`is_inferred`、`coordinate_accuracy`、`historicalRegionName`、`stillExists` 字段 API 已返回,但 `AtlasMap.tsx` 对推定地点仍画实心标记;应把 `coordinate_accuracy='inferred'` 画成虚线光晕,把 region/country 类型画成模糊区域面而非点。
- **为什么**:这是学术可信度的可视化表达(v3.1 政策「坐标不是事件真实性证明」),也是与随意的「圣经地图」产品拉开差距的细节;扩容后 200+ 地点中推定坐标比例会显著上升,不区分会误导。
- **工作量**:S(样式区分)/ M(区域面需要 GeoJSON 多边形数据,可从 OpenBible/Natural Earth 引入)。
- **依赖/风险**:区域面数据需新增字段或表;先做 S 部分即可。

## 二、内容与数据

### 2.1 AI 辅助内容生成管线:固化为可复用资产 —— 强烈推荐,M

- **主张**:把本次「13 个时代并行代理生成种子」的做法固化成一条显式管线:`共享规范(UUID 前缀/sequence 区间/双语/宽年代/来源)→ LLM 生成 SQL 种子 → 自动校验器 → 人工抽检 → 装载`,然后用它扩充其余四部作品。
- **为什么**:这条管线是本项目目前最独特的能力——HANDOFF 中的 UUID 分区(`人物 43/事件 33/关系 63/其他 73` + 时代编号)和 sequence 区间(`K*1000+1..999`)已经是并行生成的工程化约定,只差把「校验」从人工变成脚本(见 2.2)。四部占位作品(双城记、安妮日记、牧羊少年、霍比特人)每部按 40–80 人物/100–300 事件规模生成,成本约为圣经的零头,却能把产品从「圣经地图」变成「文学地图平台」。
- **工作量**:M(管线脚本化 S–M;四部作品内容生成与审校各 1–2 天)。
- **依赖/风险**:①版权——《安妮日记》《牧羊少年》仍在版权期,严守既有政策(只存原创结构化摘要与短引用标识,不存原文段落);②幻觉——虚构作品的事件地点需对照文本核验,`confidence`/`reality_type` 字段必须如实标注;③《霍比特人》走 fictional canvas(`canvas_x/canvas_y`),生成规范需单独一版。

### 2.2 数据校验器与 CI 化 invariants —— 强烈推荐,S

- **主张**:把数据纪律写成一个 `npm run verify:data` 脚本:每事件 ≥1 人物/地点/来源、双语 published 齐全、sequence 无冲突、`historical_start_year` 落在所属 chapter 的 `era_start/end_year` 内、关系两端人物存在、UUID 前缀符合分区规范。
- **为什么**:HANDOFF 下一步就是「装载 13 个种子文件 + 修复装载错误」,没有校验器时错误靠 Postgres 约束和肉眼;13 个并行代理的产物合并是最容易出「跨文件冲突」(sequence、slug、关系引用)的时刻。这也是 2.1 管线的核心零件——校验器越强,LLM 生成越可放心并行。
- **工作量**:S。
- **依赖/风险**:无。这是当前阶段性价比最高的一条。

### 2.3 media_assets 填充:Wikimedia Commons 管线 —— 试点完成，分批推进

- **当前状态(2026-08-09)**:已完成最小闭环：人物、事件、地点各 1 条 bundled + verified 公有领域媒体；图片本地托管，Commons provenance、双语 alt、语义角色/状态和 checksum 均有验证器覆盖。
- **产品纪律**:character_depiction 不是历史肖像，event_scene 不是现场记录，place_view 的现代地点照片不等同于古代场景。未验证许可继续走 external-link-only，不以远程图片兜底。
- **下一批**:优先策展少量高价值人物/地点/事件，按同一 seed + verifier 批次提交；每批先做人工来源核对，再装载、校验和浏览器抽检，不直接按数量抓取。
- **工作量**:后续每批 M（筛选、下载、双语 alt、provenance、checksum、抽屉抽检）。
- **依赖/风险**:图片托管会增加静态包体；需在下一批前测量首屏/抽屉加载与包体，必要时改为尺寸变体或懒加载，但不得牺牲权利与语义声明。

### 2.4 外部数据对齐:OpenBible Geocoding / Pleiades ID —— 推荐,S/M

- **主张**:给 `locations` 增加 `external_refs jsonb`(openbible slug、Pleiades ID、Wikidata QID),用 OpenBible 的开放数据(GitHub: openbibleinfo/Bible-Geocoding-Data)交叉校验 250 个地点的坐标与 `coordinate_accuracy`。
- **为什么**:坐标是本项目最容易被专业读者挑错的地方;OpenBible 已把「每个圣经地名的候选位置与置信度」做成开放数据,对齐一次即可完成一轮免费的权威校验,并为将来的互链(Pelagios 生态)留接口。
- **工作量**:S(加列 + 脚本比对报告)/ M(逐条裁决差异)。
- **依赖/风险**:两边 slug 对齐需要模糊匹配 + 人工确认;它的许可是 CC-BY,引用需在 `sources` 表记账。

### 2.5 社区共建/众包数据管线 —— 明确不做(现阶段),L

- **主张**:暂缓。不建众包提交、审核、账号体系;以「GitHub Issue + 种子 PR」作为唯一外部纠错通道,在页面脚注放数据反馈链接即可。
- **为什么**:Recogito 的经验是众包需要专门标注工具、审核流与动机设计,且核验率不足一半;本项目尚无线上版本、无受众,众包管线是「为不存在的贡献者造工厂」。AI 管线(2.1)+ 校验器(2.2)在当前规模下比众包更快更稳。
- **工作量**:L(故不做)。
- **依赖/风险**:若未来教育场景成型(1.4),可参考 Pelagios「课堂众包」模式小规模试点,那时再评估。

## 三、技术架构

### 3.1 1500 事件后的性能收口:测量、索引、Worker —— 必做,M

- **主张**:装载完成后立即做一轮性能收口:①实测 `/atlas?detail=lite` 载荷(预估 1.5–3 MB),开 gzip/br 压缩与 ETag;②把 `hierarchy.ts`/`AtlasMap.tsx` 中所有 `atlas.events.find`/`atlas.characters.find` 线性查找换成一次性构建的 Map 索引(`trajectoryFor`、`relationVisibleAtSequence`、`chapterForLocation` 都是 O(n²) 热点);③Zod 全量 `parse` 移入 Web Worker 或换 `safeParse` 抽样校验,避免主线程卡顿;④`TimelineRibbon` 6 泳道对 1500 事件的绘制做 chapter 级聚合(时代内只画密度条,选中时代才画单事件)。
- **为什么**:这是 REDESIGN_PLAN 早就点名的「第一道硬墙」,而且是所有体验方向(播放、动画)的前置条件;v4 验收标准「首屏 < 2s,交互 60fps」尚未在真实规模下验证过。`EntityList` 已用 `@tanstack/react-virtual`,列表侧无忧,热点在派生计算与地图/时间轴。
- **工作量**:M。
- **依赖/风险**:先测量再优化——用装载后的真实数据跑一次 Lighthouse/Profiler,避免优化想象中的瓶颈。

### 3.2 静态化线上部署:把只读 API 烘焙成 JSON —— 强烈推荐,S/M

- **主张**:数据是纯只读的,不需要线上跑 Express+PostGIS。加一个 `npm run bake` 脚本:遍历 5 作品 × 2 locale,把 `/api/works`、`/atlas?detail=lite`、每实体 detail、搜索索引全部写成静态 JSON;前端 `api.ts` 只需把 `base` 换成静态目录(30 行文件,一处改动);部署到 Cloudflare Pages/GitHub Pages。
- **为什么**:这是「有无线上版本」的分水岭,而本项目架构恰好对静态化极度友好——`api.ts` 是唯一网络层,全部端点都是纯 GET 幂等查询;深链接(`serializeAtlasState`)只有在有公网 URL 时才产生真实价值。搜索可降级为前端在 lite 索引上过滤(`hierarchy.ts` 的 `matchesQuery` 已存在,`/api/search` 的服务端版本仅在本地开发保留)。零服务器成本、零运维、天然 CDN。
- **工作量**:S(bake 脚本 + base 切换)/ M(加 SPA 路由回退、per-entity OG 标签预渲染)。
- **依赖/风险**:实体 detail 端点会烘焙出 ~2000×2 个小 JSON 文件,数量无害;放弃了未来「写操作」的即时性——但在众包(2.5)明确不做的前提下没有代价。Docker/Postgres 流程保留为「内容生产环境」,线上是其构建产物。

### 3.3 移动端 PWA:静态化的顺手收益 —— 推荐排后,S

- **主张**:在 3.2 之上加 manifest + Service Worker,把 lite atlas JSON 与经文 JSON 按作品缓存,做到离线可查。
- **为什么**:圣经查考场景(教会、课堂、无网环境)与 PWA 离线高度契合;静态 JSON 让缓存策略变得平凡(URL 即版本)。但注意:`styles.css` 虽已适配 375px 宽,地图+列表+时间轴三联动布局在小屏的操作动线尚未真正设计过,PWA 壳之前应先做一轮移动端布局(时间轴折叠、抽屉全屏化)。
- **工作量**:S(PWA 壳)+ M(移动布局打磨,可另立项)。
- **依赖/风险**:依赖 3.2;Leaflet 瓦片离线缓存有存储上限,离线模式可只保证数据可查、地图降级。

### 3.4 API 分层的最后一公里:按时代切分 atlas —— 备选,M

- **主张**:若 3.1 实测后 lite 载荷仍 >1.5 MB 且首屏超标,把 atlas 再切成 `atlas-core.json`(works/chapters/groups/chronologies/locations)+ 每时代一个 `events-{chapter}.json`,按 era-rail 的可视需要懒加载。
- **为什么**:这是 REDESIGN_PLAN 主张 2「索引+按需」的完整形态,但**只有测量证明需要时才做**——单文件 gzip 后若在 400 KB 以内,切分带来的状态管理复杂度(跨时代搜索、关系图需要全量人物)不划算。
- **工作量**:M。
- **依赖/风险**:与 3.2 的 bake 脚本天然兼容(多烘几个文件而已);风险是 `hierarchy.ts` 的「单一派生」假设全量在内存,切分后需要显式的「已加载时代」状态。

### 3.5 内容页 SSG 与 SEO —— 备选,M/L

- **主张**:为每个人物/地点/事件预渲染一个静态 HTML 页(标题、摘要、OG 图、指回主应用深链接),挂在 `/p/{work}/{kind}/{slug}` 路径。
- **为什么**:主应用是纯 SPA,搜索引擎与社交分享几乎抓不到内容;300 人物 × 双语 = 600 个长尾入口页,是零成本获客的主通道。但应在内容(媒体、经文联动)充实后再做,否则页面单薄。
- **工作量**:M(模板化生成)/ L(若引入完整 SSR 框架——不建议,用 bake 思路生成即可)。
- **依赖/风险**:依赖 3.2、2.3。

## 四、增长与形态

### 4.1 线上部署 + 深链接分享:第一优先的形态跃迁 —— 强烈推荐(=3.2 的产品面)

- **主张**:上线后把「复制链接」按钮(`App.tsx` 的 copy 按钮已存在)升级为「分享此刻」:任何 时代/时间窗/选中实体/缩放层级 的组合都是一个可发出去的 URL,配 per-entity OG 卡片。
- **为什么**:全部状态序列化早已完成(`serializeAtlasState` 写入 locale/works/zoom/era/until/entity),这是已付成本、未收回报的功能;没有公网 URL,双语、深链接、故事线全都只对一个人可见。
- **工作量**:含在 3.2;OG 卡片生成 +S。
- **依赖/风险**:无新风险。

### 4.2 多作品对照:降级为「保留但不投入」 —— 建议收缩

- **主张**:保留现有五选对照的基础设施(`validateWorkSelection`、compare-bar、同层规则),但不再为它开发新功能;把「对照」的叙事重心转向**圣经内部**:时代 vs 时代、人物旅程 vs 人物旅程(如摩西路线与保罗路线同图)。
- **为什么**:诚实评估——《双城记》与《牧羊少年》没有共享的地点、时间或人物,叠在一张地图上除了「都在地球上」没有可比语义;真实的对照价值来自共享维度(同一地区、同一时代、互文关系),而目录里只有圣经内部具备这种密度。等其余四部数据充实(2.1)且出现同地区作品(如巴黎的《悲惨世界》vs《双城记》)时,对照才会自然有用。
- **工作量**:0(收缩即节省)。
- **依赖/风险**:注意 `state.ts` 的 MAX_SELECTED_WORKS 与 mixed_layers 逻辑已稳定,不动即可。

### 4.3 教育/课堂形态:故事线 + 可打印图卡 —— 中期方向,M

- **主张**:以 1.4 的故事线为骨架,提供「课堂模式」:全屏地图 + 大字号时间轴 + 教师逐步推进;并为每个时代生成可打印的 A4 摘要图卡(人物群 + 地图 + 时间带)。
- **为什么**:圣经地理是主日学与人文课的刚需教具;这是 Recogito「课堂众包」的反向应用——先用课堂做分发,将来才可能有社区共建的土壤。差异化在双语:同一教具可服务中文与英文班级。
- **工作量**:M。
- **依赖/风险**:依赖 1.1/1.4 与线上部署;打印样式是被低估的工作量。

### 4.4 「可提问的动词」:从浏览工具到问答入口 —— 远期,L

- **主张**:借鉴 ORBIS 的成功要素,提供 2–3 个具体可操作的问题入口:「X 和 Y 见过面吗?」(关系图路径查询)、「这一年世界上正在发生什么?」(时间切片跨时代视图)、「从 A 到 B 有多远?」(基于 routes 的旅程测算)。
- **为什么**:ORBIS 的传播力来自「它能回答一个你说得出口的问题」;本项目数据模型(关系生命周期、事件年代、路线 waypoints)已经支撑得起前两个问题,只缺查询 UI。
- **工作量**:L(每个问题入口 M)。
- **依赖/风险**:排在数据规模与性能收口之后;避免做成通用查询器,只做预设问题模板。

## 六、推荐路线图(1500 事件装载完成后的 3 个里程碑)

### M1 · 规模落地与质量闸门(约 1 周)
装载 13 个种子(`010–022`)+ sequence 重排(023)→ **先写数据校验器(2.2)再装载**,用它清剩余错误 → 性能收口(3.1:gzip、Map 索引、Worker parse、时间轴时代聚合)→ 在真实规模下跑一遍 v4 验收标准(首屏 <2s、60fps)。
**理由**:一切体验与增长方向都建立在「1500 事件真的能流畅跑」之上;校验器同时是 M3 内容管线的零件,一次投入两次收益。

### M2 · 上线与分享(约 1 周)
静态化 bake 脚本 + Cloudflare Pages 部署(3.2)→ 分享按钮与 OG 卡片(4.1)→ PWA 壳与离线缓存基础(3.3 的 S 部分)。
**理由**:这是产品从「本地 Demo」到「可传播产品」的形态跃迁,且工作量最小(S/M);上线后每一个后续功能的反馈循环都缩短——没有比「把已完成的 300 人物版本给人看」更高优先级的事。

### M3 · 叙事化体验包(约 2 周)
时间轴播放(1.1)→ 人物旅程动画(1.2)→ 经文引用联动(1.3)→ 首批 3 条故事线(1.4:出埃及、大卫、保罗宣教)。
**理由**:这三件事共同回答「用户来了看什么」:播放给第一分钟的惊艳,旅程动画给传播素材,经文联动给可信度与留存。完成后产品对标面上无直接竞品(OpenBible 有数据无叙事,ORBIS 有模型无文本联动)。

**M3 之后**:media_assets 填充(2.3)与 OpenBible 坐标对齐(2.4)→ AI 管线扩四部作品(2.1)→ 图分析模式(1.5)→ SSG 内容页(3.5)。
