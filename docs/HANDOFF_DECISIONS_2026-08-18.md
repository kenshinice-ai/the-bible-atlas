# Handoff 决策补充 · 2026-08-18（Bible 艺术与音乐升级 A/B/C/D）

本文件记录本轮四条轨（A 人物视觉身份、B 重要言论、C 音乐维度、D 全域艺术表达）的执行决策与证据边界。规划见 [BIBLE_ART_MUSIC_UPGRADE_PLAN_2026-08-18.md](BIBLE_ART_MUSIC_UPGRADE_PLAN_2026-08-18.md)。**本轮已通过神职/设计双重评审并发布 production（deployment `df0d2736`，commit `c57919e`）。**

## 1. 决策 BA-D001：人物身份走符号，不走肖像

圣经人物没有同时代肖像，任何"头像"都只能是后世艺术、现代生成或符号三选一。本项目选**符号**为全站身份标识（纹章徽章），公版艺术描绘退居抽屉内的接受史区块。

- 徽章不宣称容貌，只宣称"传统用此记号指认此人"，每条记录必须标注 attestation：`scriptural`（经文直证）/ `liturgical`（礼仪传统）/ `iconographic`（图像学传统）。
- 不为上帝设徽章；耶稣使用 Chi-Rho 字母符号而非面容——具象描绘在多个传统中属敏感问题，符号是中立表达。
- 不发明新符号。40 条策展徽章全部有经文或长期传统出处，写入 `symbol_meaning`。
- 无策展记录的人物走**程序回退**：以 slug 为种子的确定性图形，属同一视觉族群但不承载语义。
- `PersonAvatar` 在存在徽章数据时整体替换旧剪影：剪影暗示身体，本图集对任何人的身体没有证据。

## 2. 决策 BA-D002：引文必须逐字比对公版经文才能出现在界面上

- 译本白名单固定为**和合本（CUV, 1919）**与 **World English Bible**。**排除 KJV**：其在英国受永久性 Crown copyright 约束，对面向全球的静态站点不是无争议选项。这是对 EVOLUTION_DIRECTIONS 1.3 的一处修正。
- 和合本按其**出版时的繁体形态**存储，UI 以 `lang="zh-Hant"` 呈现并标注「和合本（1919，繁体）」。不做繁简转换：把 1919 年版本改写成它没有印过的字形，会让"已核验"这个标签失去意义。与山海经域展示原文的做法一致。
- 数据契约要求 `text_status='source_verified'` 时必须同时具备：HTTPS 来源 URL、取回时间戳、取回整节原文及其 SHA-256，且**展示引文必须是取回原文的连续子串**——该约束由 Postgres CHECK 强制，不只靠脚本。
- API 只输出 `source_verified` 且 published 的引文；未核验的条目不进入 payload，而不是带着一句没人读的免责声明上线。
- 生成器在本轮抓出 14 处真实转写差异（弯引号、和合本异体字「裏/着/作」、编者夹注、WEB 间接引语），全部按源文本订正后 38 条引文 × 2 语言全部通过。

## 3. 决策 BA-D003：跨作品链接做成通用契约

`cross_work_links` 不是圣经专用表。美术史↔圣经、音乐史↔圣经、以及将来的其他组合都会需要它，因此定义为 `(from_work, from_kind, from_id) → (to_work, to_kind, to_id) + link_type`，并禁止同作品自链（同域关系属于既有领域表）。

- 链接类型只有 `musical_setting`（为该经文谱曲）与 `musical_reception`（取材于该叙事），每条必须写明依据（`basis_note`），空依据不允许入库。
- 音频**不新增**：全部复用音乐图集既有的自产合成学习音，播放免责声明随链接跨作品边界一起传递，不在边界处丢失。
- API 在圣经 payload 内联解析曲名、作曲家与一段可播放片段——圣经 payload 不携带音乐图集，否则客户端要为一张卡片再拉一份大得多的 atlas。
- Tallis《Spem in alium》取材《友第德传》属次经，当前 profile 无对应实体，**不为链接方便而伪造实体**，记为已知缺口。

## 4. 决策 BA-D004：总览图是装饰底图，不是地理主张

- `scripts/generate_bible_overview.ts` 从本图集自己的地点坐标、路线顺序与时代色确定性渲染，同库状态产出字节一致的 SVG，manifest 记录生成器版本与 checksum。
- 明确标注 `artistic_interpretation`：位置主张只属于 Leaflet 交互图层。使用手抄本舆图语法（罗盘线、风玫瑰、藤蔓边框）正是为了说"这是被制作出来的图像"。
- 视觉调整两处出于真实问题：地点权重改**对数缩放**（线性时耶路撒冷的光晕吞掉整个黎凡特），风玫瑰移出质心（居中时正压在耶路撒冷上，像一次爆炸）。

## 5. 决策 BA-D005：多雷批次范围与新约推迟

- 首批 25 张全部取自 Doré's English Bible（1866）希伯来圣经部分，作者卒于 1883，全球公有领域，权利立场无争议。
- 每条记录固定为 `illustrative`：十九世纪版画是 1866 年如何想象这段叙事的证据，不是任何人容貌的证据。
- **新约批次推迟**，特别是"本图集是否应当收录耶稣的具象描绘"——徽章体系刻意不画他，媒体层是否可以画他是一个需要 liturgical design review 判断的问题，不由本轮单方面决定。
- 导入器改为可续跑：Wikimedia 对这种体量的批量抓取限流很紧，重复下载既慢又不礼貌。

## 6. 校验器决策：从冻结清单改为数据库驱动

`verify_bible_visual_media.ts` 原本硬编码 3 条试点资产。硬编码清单在下一批落地的那一刻就不再是校验——它要么挡住新批次，要么被改成迎合新批次。现改为：

- 资产清单由数据库驱动，**策略**保持硬编码（许可白名单、必需的 provenance 字段、允许的语义角色）；
- 自产生成资产走独立允许清单并比对 manifest checksum；
- 媒体目录中任何无法解释的文件仍然导致失败。

新增 `verify_bible_art_music.ts` 覆盖徽章、经文引用、引文、跨作品链接与总览图五项契约，全部 fail-closed。

## 7. 环境修复（非本轮功能范围）

`scripts/verify_postgis.sh` 在本机无法启动临时实例，报 `postmaster became multithreaded during startup`。这是 PostgreSQL 18 在 macOS 上未设 LC_ALL 时的已知行为，与本轮改动无关。脚本已加入 `export LC_ALL=${LC_ALL:-C}`（一次性临时库不含区域相关数据），否则该门禁在本机完全无法运行。

## 10. 决策 BA-D006：新约批次收录耶稣的具象描绘，按四条件执行

评审建议收录，本轮采纳。核心论证值得原样保留:**不画耶稣不是中立位置**——第二次尼西亚会议（787）以道成肉身为据正面肯定基督可被描绘，海德堡要理问答第 98 问与韦斯敏斯特大要理问答第 109 问则禁止；二者都是有份量的传统。更要紧的是内部一致性：本图集已经收录了多雷的摩西、以利亚、但以理，按同一条十诫解释，这些图像与基督像同样在禁列。单为耶稣一人破例，是悄悄采纳了某一传统关于某一位人物的特定规则，并把它伪装成中立。

四条件的落实：

1. **徽章层不动**。耶稣继续用 Chi-Rho，身份层保持无像。分工因此才有意义：徽章说"这是他的身份记号"，图像说"这是 1866 年的想象"。
2. **全部归入显式「后世接受」分组**（S1 已落地的抽屉分隔线），`illustrative`，与希伯来圣经批次同规格。
3. 耶稣条目补一句说明：具象描绘在部分传统中被肯定、在另一些传统中被拒绝，本图集两者都不代读者决定。
4. **受难系列不在本批**。十九世纪受难图像学在祭司长与人群的处理上普遍带有当时的敌犹视觉成规；客西马尼之后的全部情节、进耶路撒冷、最后晚餐，以及司提反被石打（同为「群众即控告者」构图），一律留待单独成批、逐张过目。

**执行状态（2026-08-18）**：批次已定稿并通过权利探测，但 Wikimedia 在抓取途中对本地址开始限流（curl 与 Node 同样收到 429），14 张中完成 6 张，seed `072` 未生成，**本次发布不含新约批次**。导入器支持续跑：`npm run import:bible-dore-media new-testament` 会跳过已在盘的文件。已下载的 6 张暂存在会话 scratchpad 的 `nt-partial/`，续跑前放回 `apps/web/public/media/bible/dore/` 可省去重复抓取；不放回也只是重下。

批次外的一个实际结果：多雷《山上宝训》的 Commons 文件页没有作者字段，权利门禁拒收。一张所有人都看得出出自谁手的版画，在可归属之前仍然不能发布——换用了署名完整的另一张。

## 11. 决策 BA-D007：山海经与红楼梦迁出，`020/021` 直接删除而非保留

两条线已由用户迁入独立项目。删除前逐项核验：山海经语料 JSON 与程序化母图在新项目中 SHA-256 完全相同，文档 33 篇对 31 篇为超集，且新仓库有独立 git 历史；红楼梦蓝图在新项目中同为超集，本仓库的原型组件无任何引用。

迁移号的处理是唯一需要判断的地方。本项目的 migration runner 是前向、按版本记录的，因此有两种做法：

- 保留 `020/021` 再加一个 drop —— 历史仍然完整，但**山海经的 schema 仍留在本仓库里**，等于没有迁出；
- 直接删除 `020/021`，并用 `023` 幂等清理既有库 —— 全新 bootstrap 从不建这些表，旧库被收敛。

选后者。理由是"移除"的语义应当是真的移除；而已装载库的收敛由 `023` 的 `DROP IF EXISTS` 负责，两种状态都收得住。本仓库 git 历史仍完整保留这两条线，需要时可取回。

`mythography` 枚举值保留在 `work_category` 中：从 Postgres 枚举删值要重建类型与全部引用列，这是真实风险，换来的只是无人看得见的整洁。
